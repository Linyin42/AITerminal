## 0. 先读：管线长什么样

```
knowledge/<vendor>/tech/*.md           ← 你要产出的东西（唯一手工交付物）
      │  build_index.py --vendor <v> --chunk      （纯代码切块，不调模型）
      ▼
<ROOT>/index/<vendor>_chunks.jsonl     ← 每行一个片段（JSON）
      │  embed_chunks.py --vendor <v>             （调 :8081 的 bge-m3）
      ▼
<ROOT>/index/<vendor>_emb.f16          ← float16 向量矩阵，行号 ↔ jsonl 行号
<ROOT>/index/<vendor>_emb.meta.json    ← 断点与形状元数据
      │  retrieve.py（numpy 暴力点积）
      ▼
core/local_rag.py → ai.ask 注入提示词 → 界面回答带出处
```
依据：`local_llm/build_index.py:12-14`、`local_llm/embed_chunks.py:2-10`、`local_llm/retrieve.py:1-15`、`core/local_rag.py:1-9`。

**三条必须先记住的结论**

1. **界面上的「导入资料」按钮不属于这条管线。** 它把文件复制进 `~/.aiterminal/knowledge/` 并建 `.index.json` 词法索引（`core/knowledge.py:34-35`、`core/knowledge.py:505-537`），**不产生** `<vendor>_emb.f16`；向量管线只认 `knowledge/<vendor>/tech/*.md` + `<ROOT>/index/` 三件套（`core/local_rag.py:53-75`）。想"导入后向量检索就能用"，必须走本规范的路径。
2. **切片与向量不由你手写。** `chunks.jsonl` / `.f16` / `meta.json` 三件全部由代码生成；你只要交 `.md`（第 6 章）。第 3 章的字段规范是**契约**：只有当你绕过 `build_index.py` 自带切片时才需要逐字遵守。
3. **一个厂商 = 1 个输入目录 + 3 个产物文件，缺一不可。** 应用侧用"三件齐"判定该厂商可用：`<v>_emb.meta.json` + `<v>_chunks.jsonl` + `<v>_emb.f16`（`core/local_rag.py:64-70`）。

## 1. 目录与文件布局

### 1.1 一个厂商需要哪些文件

| 角色 | 路径 | 谁产生 | 作用 | 依据 |
|---|---|---|---|---|
| **输入（必交）** | `knowledge/<vendor>/tech/*.md` | **你** | 技术讲解正文，按 feature 一文件 | `build_index.py:28-29`、`build_index.py:205-212` |
| 输入（可选） | `knowledge/<vendor>/tech/ai/*.md` | AI 产出（与厂商原文物理隔离） | 仅在加 `--include-ai` 时纳入切片 | `build_index.py:213-218`、`core/tech_knowledge.py:19-21` |
| 切片 | `<ROOT>/index/<vendor>_chunks.jsonl` | `build_index.py` | 每行一个片段 | `build_index.py:225` |
| 向量 | `<ROOT>/index/<vendor>_emb.f16` | `embed_chunks.py` | fp16 矩阵 `(n, 1024)`，L2 已归一化 | `embed_chunks.py:190`、`embed_chunks.py:203-204` |
| 元数据 | `<ROOT>/index/<vendor>_emb.meta.json` | `embed_chunks.py` | 形状 + 断点 + 失败数 | `embed_chunks.py:191`、`embed_chunks.py:54-58` |
| 模型 | `<ROOT>/models/bge-m3-Q8_0.gguf` | `download_models.py core` | 嵌入模型 | `embed_chunks.py:31`、`embed_chunks.py:80-81` |
| 二进制 | `<ROOT>/bin/llamacpp-{vulkan,cuda,cpu}/llama-server.exe` | `download_llamacpp.py` | 起 :8081 / :8080 | `paths.py:74-79`、`paths.py:82-90` |

注：`<vendor>` 是**同一个字符串**出现在 4 个地方——目录名、`--vendor` 参数、`<vendor>_chunks.jsonl`/`<vendor>_emb.*` 文件名、`chunks.jsonl` 的 `vendor` 字段（`build_index.py:205`、`build_index.py:225`、`build_index.py:185`）。代码未做大小写归一（`build_index.py:198` 直接用 `args.vendor`），而 `core/tech_knowledge.py:55` 会 `lower()`；**统一用小写 ASCII**（现有四家：`h3c` `huawei` `ruijie` `tplink`，实测 `D:\ait_llm\index`）。

### 1.2 `<ROOT>`（索引与模型放哪）怎么定

按优先级取第一个可用者（`paths.py:52-66`）：

1. 环境变量 `AIT_LLM_HOME`（`paths.py:55-57`）
2. 打包态且 exe 同目录有 `llm_data/` → 用它（`paths.py:39-49`、`paths.py:58-60`）
3. **`D:\ait_llm`**（只要 `D:` 盘存在就用它，不看目录在不在，`paths.py:63-65`）
4. 兜底 `<仓库>/local_llm/llm_data`（`paths.py:29`、`paths.py:66`）

子目录固定为 `bin/` `models/` `index/`（`paths.py:70-72`）。**先跑 `python paths.py` 确认实际用的是哪个根**（`paths.py:116-128`）。

### 1.3 输入目录的硬要求

- 目录必须是 `knowledge/<vendor>/tech/`，**不存在就直接报错退出**：`!! 目录不存在: <base>`（`build_index.py:205-207`）。
- 只收 `tech/` **顶层**的 `.md`（不递归）；`--include-ai` 才额外收 `tech/ai/*.md`（`build_index.py:209-218`）。子目录里的 md 会被**静默忽略**。
- 非 `.md` 文件（如 `tech/index.json`）不参与切片（`build_index.py:211`）；但 `tech/index.json` 是 `core/tech_knowledge.py` 需要的另一个索引，与向量管线无关（`core/tech_knowledge.py:59-64`）。**交数据时请一并保留 `index.json`**，否则"技术"页签不可用。
- `build_index.py` 里的 `KNOWLEDGE` 是**按脚本位置**推的 `<仓库根>/knowledge`（`build_index.py:28-29`），**不读** `AIT_KNOWLEDGE_DIR`（对比 `core/tech_knowledge.py:50-51` 读它）。所以：把 md 放仓库的 `knowledge/` 下，别指望用环境变量换位置。

## 2. 原始资料要求

### 2.1 文件格式

- **能收**：`.md`（唯一被切片器读取的格式，`build_index.py:211`）。
- 界面「导入资料」按钮能收的格式**与本管线无关**，仅列出备查：文本类 `.txt .md .markdown .log .cfg .conf .ini .json .yaml .yml .csv .tsv .xml .rst .text`；需解析类 `.pdf .docx .xlsx .pptx .html .htm .zip .hdx`（`core/knowledge.py:39-44`、`core/knowledge.py:54`）；**不支持** `.doc .xls .ppt .rar .7z`（`core/knowledge.py:46-52`）。这些文件走的是词法层，不会进向量库。
- 图片（png/jpg）、PDF、CHM 等**不能直接进向量管线**；必须先由代码/工具转成 `.md` 文本（现有 `tools/build_tech_docs.py:1-18`、`tools/hdx_to_tech.py`）。向量只对 `text` 字段算（`embed_chunks.py:173-179`），**没有任何图片处理路径**（未在代码中确认）。

### 2.2 编码（最容易静默坏的一环）

- **必须是 UTF-8**。切片器用 `open(path, "r", encoding="utf-8", errors="replace")`（`build_index.py:174`、`build_index.py:233`）：**GBK/GB18030 文件不会报错**，只会把中文整段替换成 `�`，一路进向量库。自检命令见 §6.3。
- **不要写 BOM**。读取用的是 `utf-8`（不是 `utf-8-sig`），BOM 会粘在首行；若首行正好是 `### 标题`，`HEAD_RE`（`build_index.py:40`）匹配不上，**第一小节整段丢失**（机制依据 `build_index.py:85-95`）。
- 换行统一 LF/CRLF 均可（`splitlines()` 处理，`build_index.py:85`、`build_index.py:114`）。

### 2.3 命名与目录组织

- 一个 feature（功能分类）一个文件，文件名可读即可，代码只按 `*.md` 收集、按文件名排序（`build_index.py:209-212`）。文件名会成为出处的一半（`file = "tech/<文件名>"`，`build_index.py:212`），**改文件名等于改出处**。
- 目录层级就是"厂商 / tech / 文件"三层，**不要自建更深层**（深层 md 会被忽略，见 §1.3）。
- 推荐文件名 = `<功能分类>.md`，与头部 `- 功能分类：` 一致（现有数据即如此：`knowledge/h3c/tech/ACL和QoS-ACL.md` 的 `功能分类：ACL和QoS/ACL`）。文件名含 `/` 不行（`ACL和QoS/ACL` 被写成 `ACL和QoS-ACL.md`）。

### 2.4 标题层级（必需，决定能不能切出片段）

- 切片边界只认 **`##` ~ `####`**（正则 `^(#{2,4})\s+(.*\S)\s*$`，`build_index.py:40`）。要求：
  - **`#` 一级标题不算小节**，它前面（含它自己）的所有内容**整段丢弃**——"第一个标题之前的内容整体丢弃"（`build_index.py:74-81`、`build_index.py:94-95`）。所以免责声明、版权、生成信息放文件头是**安全**的（会被丢掉）。
  - `#` 后面**必须有空格**：`###标题` 不是标题，会被当正文（`build_index.py:40` 的 `\s+`）。
  - 正文里以 `#` 开头的**设备配置注释行**（如 `# 开启 DHCP 功能`）不会被误判为标题——因为它们只有一个 `#`（实测：h3c 前 5 个文件共 155 行以 `# ` 开头，其中每文件仅 1 行是文件标题、其余是配置注释，均未被当作小节边界）。
  - `#####` 及以上不是边界（`{2,4}`），会留在正文里。
- **同一文件内小节标题应唯一**：检索层按 `(file, section)` 去重（`core/local_rag.py:127-131`），同文件同名的两个小节会被当成同一个出处，只保留分数高的那条。
- 标题层级建议：文件头 `#`，小节用 `###`（现有数据如此）。

### 2.5 头部元信息块（决定片段前缀）

- `- 功能分类：<值>` 这一行会被单独解析，作为每个片段的语境前缀（正则 `^-\s*功能分类：\s*(.+?)\s*$`，`build_index.py:60`、`build_index.py:63-71`），**只在文件前 20 行、且只读前 4096 字节内生效**（`build_index.py:66`、`build_index.py:234`）。
- 最终片段首行是 `[<vendor> · <功能分类> · <小节标题>]`（`build_index.py:181-183`）。`功能分类` 缺失时前缀会少一段（`.strip(" ·")` 兜底，`build_index.py:181`），**不报错但检索语境变差**。
- 头部示例（可直接照抄，来自 `knowledge/h3c/tech/ACL和QoS-ACL.md:1-11`）：

```markdown
# H3C · ACL和QoS/ACL

> 本文件由 `tools/build_tech_docs.py` 从**厂商原始文档**用代码提取，未经 AI 改写。
> 提取不到正文时**留空并说明**，不做任何补写。

- 厂商：h3c
- 功能分类：ACL和QoS/ACL
- 命令条数：27
- 来源文档：9 个
- 生成时间：2026-10-06 23:38:27

---

### 1.3  配置ACL

<!-- source: h3c_cr16000/09-ACL和QoS配置指导/html/1168351695_1838026174_-529662947.htm -->

<正文…>
```
（除 `功能分类` 外，其余头部行只是人看的，代码不读——`build_index.py:63-71` 只找 `功能分类`。）

### 2.6 出处行 `<!-- source: … -->`（强烈建议）

- 格式：HTML 注释，正则 `<!--\s*source:\s*(.+?)\s*-->`（`build_index.py:59`）。
- 位置：必须在**该小节任何非空正文之前**（含空行之后也可以）。判定是"缓冲区里还没有非空行"（`build_index.py:96-99`）；一旦前面已有正文，这行会被**当成正文留在 text 里**，`source` 变空。
- 每个小节取**第一条**（`build_index.py:96-98`），其余同格式注释按普通正文处理。
- 它一路带到回答里：`build_context` 会拼 `原始出处：…`（`retrieve.py` 的 `build_context` 块），应用提示词要求标注来源（`core/local_rag.py:149-153`）。
- 实测有 4.3% 的片段 `source` 为空（h3c 4057/93629、huawei 8076/186502、ruijie 1909/94802、tplink 66/4716）——**空 source 不会报错**，只是回答里缺出处。

### 2.7 表格与图片

- **表格**：抽取阶段已被拉平成连续长行（`build_index.py:107-111`）。切片器专门防"把表格数据行当标题"：长度 >80、含 `|`、含 `～`/`~`、以 `-` 开头的一律不是标题（`build_index.py:44-58`）。**markdown 表格的 `|` 不会导致切错**，但表格会被拆进多个片段（因为长段按行硬切，`build_index.py:128-145`）。要求：**表格前后留空行**，并保证表头与数据在同一小节内。
- **图片**：无处理路径（未在代码中确认）。图片链接 `![...](...)` 会作为普通文本行进入 `text`。**结论：重要信息不要只放图**，图里的文字必须另行转成正文，否则检索不到。

### 2.8 重复与噪声

- **没有去重逻辑**（未在代码中确认）。同一段文字出现在两个文件/两个小节 = 两个片段，都会入库。
- 噪声过滤只有一条：整节正文 `len(body) < 40` 字符直接丢弃（`MIN_CHARS`，`build_index.py:38`、`build_index.py:179-180`）。空小节、只有标题的小节不会入库。
- 文件头（第一个 `##`/`###` 之前）整段丢弃（`build_index.py:94-95`），所以"目录/免责声明"不用手工删。
- 建议（规范要求，非代码强制）：同一份内容只放一处；同一小节不要既写厂商原文又写 AI 改写（`core/tech_knowledge.py:19-21` 明确要求 AI 产出放 `tech/ai/`，与原文物理隔离）。

### 2.9 单文件体积

- **代码里没有单文件大小上限**（`build_index.py` 全文无文件大小判断）。实测最大单文件 12.1 MB（`knowledge/huawei/tech/BGP.md`，12373.7 KB），仍能切片。
- 对比：界面「导入资料」那条路有 400,000 字符上限（`core/knowledge.py:61`、`core/knowledge.py:321-333`），`.hdx` 按 350,000 字符分片（`core/knowledge.py:627`）——**与本管线无关**。
- 实践建议（实测数据支撑）：单文件别超过约 10 MB；超长文件（如 huawei `BGP.md`）会被切成很多片段，文件本身没问题，但**单行长度**要控制，见 §3.3。

## 3. `chunks.jsonl` 字段规范

> 一行一个 JSON（`json.dumps(..., ensure_ascii=False)`，`build_index.py:237`），UTF-8，无 BOM，行尾 LF/CRLF 皆可（读取按行 `json.loads`，`retrieve.py:63-66`）。
> 参考样本：`D:\ait_llm\index\h3c_chunks.jsonl` 第 1 行。

### 3.1 逐字段

| 字段 | 类型 | 是否必需 | 含义 | 典型值 | 依据 |
|---|---|---|---|---|---|
| `text` | string | **必需（硬）** | 片段正文，首行是语境前缀 `[vendor · 分类 · 小节]` | `"[h3c · ACL和QoS/ACL · 1.3  配置ACL]\n1.3 配置ACL\n…"` | `embed_chunks.py:176-179`、`build_index.py:181-183` |
| `file` | string | 必需 | 相对 `knowledge/<vendor>/tech/` 的路径 | `"tech/ACL和QoS-ACL.md"` | `build_index.py:212`、`retrieve.py:103` |
| `section` | string | 必需 | 所属小节标题（去掉 `#` 的原文） | `"1.3  配置ACL"` | `build_index.py:189`、`retrieve.py:103` |
| `source` | string | 建议（可为 `""`） | 原始出处 | `"h3c_cr16000/09-ACL和QoS配置指导/html/…htm"` | `build_index.py:190`、`retrieve.py:104` |
| `vendor` | string | 规范必需 | 厂商名，与目录/文件名一致 | `"h3c"` | `build_index.py:185` |
| `id` | int | 规范必需（检索层不读） | 0 起的写入序号，**等于 0 起行序 `i`**（jsonl 第 1 行的 `id` 是 `0`，即行号减 1） | `0` | `build_index.py:236` |
| `part` | int | 规范必需（检索层不读） | 同一小节内第几片，从 0 起 | `0`, `1` | `build_index.py:188` |
| `chars` | int | 规范必需（检索层不读） | `len(text)`（含前缀） | `1570` | `build_index.py:191` |
| `metadata` | — | **本项目没有这个字段** | — | — | 未在代码中确认存在 `metadata`；语境信息由 `text` 首行前缀 + `section`/`source` 承载（`build_index.py:181-192`） |

"检索层不读"的判定依据：`retrieve.py:99-105` 只取 `file`/`section`/`source`/`text` 四个键；`vendor` 由调用方参数决定（`retrieve.py:74-76`）。所以 `id`/`part`/`chars` 缺了不会崩，但**是自查行序对齐的唯一线索**，必须写。

### 3.2 行序契约（最硬的一条）

**第 i 行 ↔ 向量库第 i 行 ↔ `id == i` 必须严格一致。** 依据：
- `embed_chunks.py:173-179` 按行读，`texts[i]` 就是第 i 个片段；向量写到 `mm[idx + j]`（`embed_chunks.py:227-229`）。
- `retrieve.py:63-65` 用 `enumerate` 的**行号**回查片段，不用 `id`。
- `tools/check_emb_store.py:67-72` 会核对 `切片行数 == meta.n`，不等直接判 FAIL。
- 实测：四家 `id` 与行号 100% 相等（h3c 93629 / huawei 186502 / ruijie 94802 / tplink 4716 行，字段组合各只有 1 种，键集合 = `chars,file,id,part,section,source,text,vendor`）。

**因此**：`chunks.jsonl` 生成后**不要手工增删行**，也不要让某行缺 `text`——`embed_chunks.py:176-179` 对坏行是 `continue`（静默跳过），会让向量行号整体前移、与片段错位。

### 3.3 `text` 长度限制

| 界限 | 值 | 含义 | 依据 |
|---|---|---|---|
| 目标上限 | 1600 字符 | 语义段聚合目标（`MAX_CHARS`） | `build_index.py:35`、`build_index.py:148-168` |
| 硬上限（单语义段） | 4000 字符 | 超过才二次硬切（`HARD_MAX`） | `build_index.py:36`、`build_index.py:152-156` |
| 二次切分重叠 | 120 字符 | 硬切时前后重叠（`OVERLAP`） | `build_index.py:37`、`build_index.py:162-163` |
| 小节正文下限 | 40 字符 | 低于此整节丢弃（`MIN_CHARS`） | `build_index.py:38`、`build_index.py:179-180` |
| 模型上限 | 8192 token | bge-m3 上限，超了**静默截断** | `build_index.py:133-134` |

**这些是"目标"不是"保证"**（实测数据）：

- 实测超过 1600 字符的片段占比不低：h3c 16112/93629、huawei 26674/186502、ruijie 5315/94802、tplink 45/4716。原因：单个语义段 ≤4000 时**整段保留**（`build_index.py:152-156`、`build_index.py:160-165`）。
- 实测超过 4000 的仍有：h3c 4433 条、huawei 11240 条、ruijie 669 条。原因：硬切是**按行累积**，**单行自身超限不会被切开**（`build_index.py:128-145`）。实测最长片段 = huawei 20900 字符，其中单行 20834 字符（`hwEntityTrapFaultID详细描述`）。
- 实测最短片段 = 34 字符（h3c `配置调测-部署.md` 小节 `3.1.2 业务配置`，正文就是 `01-正文`）。根因：语义段被拆成 `["01-正文", <1946字>, …]` 后，聚合时"下一段自身已 >1600"会把短段单独 flush 出去，`MIN_CHARS` 只管整节正文、不管最终片段（`build_index.py:148-168`）。

**给数据准备方的要求**：正文里**不要出现超长单行**（建议任何一行 ≤500 字符）；表格式内容**逐行成行**，不要整块拼成一行。这一条比"控制文件大小"重要得多。

### 3.4 `metadata` 里放什么

本项目**没有 `metadata` 字段**（见 §3.1）。需要携带的信息请放这三处：
1. 语境前缀（自动生成）→ `[vendor · 功能分类 · 小节标题]`，来源是 `- 功能分类：` 头 + 小节标题（`build_index.py:181-183`）。
2. `section` → 小节标题原文。
3. `source` → 原始出处。

代码中未发现任何其它结构化元数据通道（未在代码中确认）。

## 4. 向量化要求

| 项 | 要求 | 依据 |
|---|---|---|
| 模型 | `bge-m3-Q8_0.gguf`（`<ROOT>/models/`） | `embed_chunks.py:31` |
| 维度 | **1024**；不等于 1024 直接 `SystemExit` | `embed_chunks.py:186-188` |
| 池化 | `--pooling cls`（bge-m3 的规定） | `embed_chunks.py:76`、`embed_chunks.py:88-90` |
| 存储精度 | `float16`，文件是 `.npy` 格式（**带 128 字节头**） | `embed_chunks.py:203-204`、`check_vectors.py:32` |
| 归一化 | 写入前 L2 归一化 ⇒ 检索时余弦 = 点积 | `embed_chunks.py:134-136`、`embed_chunks.py:213/229`、`retrieve.py:10-13` |
| 字节数校验 | `文件大小 == n × dim × 2 + 128` | `check_vectors.py:32`、`check_emb_store.py:77-82` |
| 服务 | 嵌入服务 `127.0.0.1:8081`，`POST /v1/embeddings`，`GET /health`，`Authorization: Bearer local-llm` | `embed_chunks.py:32-35`、`embed_chunks.py:103-115` |
| 服务启动 | 端口不通时脚本**自己拉起**（120s 超时，日志 `local_llm/_llama_embed.log`） | `embed_chunks.py:75-100` |
| 服务参数 | `--embedding --pooling cls -c 8192 -b 8192 -ub 8192 -ngl 99 --api-key local-llm` | `embed_chunks.py:88-90` |
| 批量 | `--batch` 默认 **32**（一次请求 32 条，超时 180s） | `embed_chunks.py:161`、`embed_chunks.py:103-104` |
| 断点粒度 | 每 `batch × 20 = 640` 片落一次 `meta.json` | `embed_chunks.py:233-234` |
| 失败兜底 | 整批失败/条数不齐 → **逐条**重试；单条超长按 3000/2000/1000/500 字符**逐步截断** | `embed_chunks.py:219-226`、`embed_chunks.py:118-131` |
| 速率参考 | 代码里用 **65 片/s** 估算 ETA | `check_vectors.py:66-67` |

**`meta.json` 记录的字段**（`embed_chunks.py:54-58`，实测四家内容一致）：

```json
{
  "vendor": "h3c",
  "n": 93629,
  "dim": 1024,
  "done": 93629,
  "failed": 0,
  "dtype": "float16",
  "normalized": true,
  "model": "bge-m3-Q8_0",
  "updated": "2026-10-16 23:58:40"
}
```
- `n` / `dim` 是**必需**的：`retrieve.load_index` 用它们打开 memmap（`retrieve.py:50-52`）。
- `done` 决定"只搜已嵌入的部分"（`retrieve.py:77`），也是续跑断点（`embed_chunks.py:193-199`）。
- `failed` 是没嵌成功的片段数（`embed_chunks.py:231`）；**这些行的向量是全零**，检索时点积为 0。

**速率与并发注意点**：嵌入任务动辄几小时（实测 huawei 186502 片）；期间**不要**执行 `run_server.py --stop`——历史上无差别 taskkill 打断过全量嵌入（`run_server.py:201-208`）。默认 `--stop` 只停本端口，`--stop-all` 才会连 :8081 一起停（`run_server.py:210-221`）。

### 5.4 断点续跑（可以）

- 续跑依据：`meta.dim == dim` **且** `meta.n == n` **且** `.f16` 存在 → 从 `done` 接着写（`embed_chunks.py:193-199`），以 `mode="r+"` 打开不丢已有行（`embed_chunks.py:203-204`）。
- `chunks.jsonl` 变了（`n` 变了）→ `done = 0` → `mode="w+"` **整文件重写**（`embed_chunks.py:196`、`embed_chunks.py:203-204`）。

```python
# -*- coding: utf-8 -*-
"""检查 knowledge/<v>/tech/*.md 的编码/结构是否满足向量管线要求（只读）。"""
import os, re, sys
v = sys.argv[1] if len(sys.argv) > 1 else "h3c"
d = os.path.join(os.path.dirname(os.path.abspath(__file__)), "knowledge", v, "tech")
HEAD = re.compile(r"^(#{2,4})\s+(.*\S)\s*$")
CAT = re.compile(r"^-\s*功能分类：\s*(.+?)\s*$")
bad = 0
for name in sorted(os.listdir(d)):
    if not name.lower().endswith(".md"):
        continue
    raw = open(os.path.join(d, name), "rb").read()
    problems = []
    if raw[:3] == b"\xef\xbb\xbf":
        problems.append("有 BOM（首个小节可能丢失）")
    try:
        text = raw.decode("utf-8")
    except UnicodeDecodeError:
        text = raw.decode("utf-8", "replace")
        problems.append("不是合法 UTF-8（中文已变 �）")
    if "�" in text:
        problems.append("含替换字符 �（编码坏了）")
    if not any(CAT.match(ln) for ln in text.splitlines()[:20]):
        problems.append("前 20 行没有「- 功能分类：」（片段前缀会缺语境）")
    heads = [m.group(2) for m in (HEAD.match(ln) for ln in text.splitlines()) if m]
    if not heads:
        problems.append("没有任何 ## ~ #### 小节（切不出片段）")
    if len(set(heads)) != len(heads):
        problems.append("同文件存在重复小节标题（会被 (file,section) 去重误合并）")
    longest = max((len(ln) for ln in text.splitlines()), default=0)
    if longest > 2000:
        problems.append("最长单行 %d 字符（会被切成超长片段）" % longest)
    if problems:
        bad += 1
        print("!! %s" % name)
        for p in problems:
            print("     - %s" % p)
print("检查 %d 个文件，有问题 %d 个" % (len([f for f in os.listdir(d) if f.lower().endswith('.md')]), bad))
```

## 7. 常见坑

### 7.1 编码坏了（症状：检索质量莫名很差，日志无报错）
**根因**：切片器 `errors="replace"`（`build_index.py:174`），GBK 文件被静默替换成 `�` 入库。
**处置**：交数据前统一转 UTF-8；用 §6.2 的 `check_md.py` 查 `�` 与 BOM。

### 7.2 空块 / 碎片（症状：命中片段只有 `01-正文` 这种残句）
**根因**：`MIN_CHARS=40` 只作用于**整节正文**（`build_index.py:179-180`）；最终片段由语义段聚合产生，短首段遇到 >1600 的下一段会被单独 flush（`build_index.py:148-168`）。
**实测**：最短片段 34 字符（h3c）。
**处置**：写 md 时让**小节开头的第一段就有实质内容**；不要把"01-正文"这类标记单独成行放在段首。

### 7.3 超长块（症状：片段被模型静默截断，检索到却答不全）
**根因**：硬切按行累积，**单行自身超限不切**（`build_index.py:128-145`）；bge-m3 上限 8192 token，超了静默截断（`build_index.py:133-134`）；嵌入时逐条兜底还会把超长文本截到 3000 字符（`embed_chunks.py:124-131`）。
**实测**：最长片段 20900 字符，其中单行 20834 字符（huawei）。
**处置**：源 md 里**任何一行不要超过约 500 字符**；把长枚举/长表格逐项换行。

### 7.4 `meta` 与 `emb` 不一致（症状：检索结果乱、或应用侧报错）
**根因**：`retrieve` 用 `meta["n"]/meta["dim"]` 打开 memmap（`retrieve.py:50-52`），文件与 meta 对不上就整体错位；`chunks.jsonl` 行数与 `meta.n` 不一致同样错位（`check_emb_store.py:67-72`）。
**处置**：任何一次重切 `chunks.jsonl` 之后**必须重跑嵌入**；交付前跑 `check_vectors.py` + `tools/check_emb_store.py`。

### 7.5 `failed != 0`（症状：`meta.json` 里 failed 有数，检索某些片段分数恒为 0）
**根因**：失败的片段行保持全零（`embed_chunks.py:227-231`），点积恒为 0；且**代码里没有"只重嵌失败行"的分支**——`done == n` 时主循环不进入（`embed_chunks.py:216`）。
**处置**：把 `meta.json` 的 `done` 改小（`0 < done < n` 时保留已有行、`mode="r+"`；`done = 0` 会 `mode="w+"` 整文件重写，见 `embed_chunks.py:196-204`）后重跑 `embed_chunks.py --vendor <v>`。**先确认失败的根因**（多半是超长片段或服务端 `-ub` 太小，`embed_chunks.py:85-90`）。

### 7.6 行号错位（症状：答案引用的出处与内容对不上）
**根因**：`chunks.jsonl` 里有坏行或缺 `text` 的行 → `embed_chunks.py:176-179` 静默跳过 → 向量行号前移；而 `retrieve.py:63-65` 按**行号**回查片段。
**处置**：`chunks.jsonl` 生成后不要手工编辑；交数据时用 §3.2 的契约自查（`id == 行号`，字段齐全）。

### 7.7 切不出任何片段（症状：`build_index.py` 报「片段 0」）
**根因**：文件只用 `#` 一级标题（`HEAD_RE` 只认 `#{2,4}`，`build_index.py:40`）；或标题与 `#` 之间没有空格；或文件被放在 `tech/` 的子目录里（不递归，`build_index.py:209-212`）。
**处置**：小节改用 `###`；确认 md 直接躺在 `knowledge/<vendor>/tech/` 下。

### 7.8 出处缺失（症状：回答里"原始出处"为空）
**根因**：`<!-- source: … -->` 不在该小节**任何非空正文之前**（`build_index.py:96-99`），于是它被当正文留下、`source` 为空。
**实测**：h3c 4.3% 片段无 source。
**处置**：把小节标题后**第一行**就写 source 注释，再空行，再写正文。

### 7.9 误停服务打断嵌入（症状：嵌入跑到一半 ConnectionResetError）
**根因**：`:8081` 的嵌入服务与 `:8080` 的对话服务是**同名进程**；`run_server.py --stop` 默认只停本端口，但 `--stop-all` 会全停（`run_server.py:201-221`）。
**处置**：嵌入期间不要 `--stop-all`；打断后靠 `meta.json` 断点续跑（§5.4）。

### 7.10 应用"能用但答不准"（症状：无任何报错）
**根因**：向量检索任何一步失败（numpy 缺失、索引没建、嵌入服务没起、切片缺列）都会**静默**退回词法层（`core/local_rag.py:11-15`、`core/local_rag.py:82-102`、`core/local_rag.py:119-125`）。
**处置**：看程序目录 `aiterminal-rag.log`；再跑 `check_emb_store.py` 与 `test_rag_retrieval.py` 定位是哪一层坏了。
